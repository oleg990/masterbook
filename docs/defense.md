# Материалы к защите MasterBook

## Краткое описание

MasterBook — веб-система для онлайн-записи клиентов к мастерам услуг.

Основной сценарий:

```text
Регистрация клиента
      -> просмотр мастеров
      -> выбор услуги
      -> выбор даты и свободного времени
      -> создание записи
      -> подтверждение мастером
      -> уведомление клиента
```

## Что показать на демонстрации

1. Открыть каталог мастеров.
2. Зарегистрировать или авторизовать клиента.
3. Открыть профиль мастера.
4. Выбрать услугу.
5. Выбрать дату и свободный слот.
6. Создать запись.
7. Показать запись со статусом `pending`.
8. Войти под мастером.
9. Подтвердить запись.
10. Вернуться к клиенту и показать уведомление.

## Какие части кода показывать

### 1. Архитектура

Показать `backend/cmd/server/main.go` и объяснить создание зависимостей:

```text
Repository -> Service -> Handler
```

### 2. AppointmentService

Показать расчёт `endTime` и проверку рабочего интервала.

### 3. AppointmentRepository

Показать транзакцию и `FOR UPDATE`.

### 4. PostgreSQL migrations

Показать внешние ключи, уникальные ограничения, статусы и проверки значений.

## Короткие ответы на вопросы комиссии

### Почему трёхслойная архитектура?

Она разделяет HTTP, бизнес-логику и доступ к данным. Благодаря этому изменение SQL не требует изменения обработчиков HTTP.

### Зачем интерфейсы Repository?

Service зависит от абстракции. В тестах вместо PostgreSQL можно использовать тестовую реализацию Repository.

### Как защищается система от двойного бронирования?

Перед созданием записи сервер повторно проверяет пересечения интервалов внутри транзакции и блокирует строку мастера через `FOR UPDATE`.

### Почему проверка доступности есть и на frontend, и на backend?

Frontend нужен для удобства пользователя. Backend остаётся источником истины, потому что между отображением свободного слота и отправкой запроса другой клиент может занять это время.

### Почему PostgreSQL?

Данные системы связаны между собой отношениями: пользователь, профиль мастера, услуга, расписание, запись и уведомление. Реляционная СУБД позволяет дополнительно обеспечивать целостность данных на уровне схемы.

### Почему Go?

Go предоставляет стандартные средства для HTTP-сервисов, простую модель конкурентного выполнения и удобный deployment одного бинарного файла.

## Что не стоит заявлять на защите

- что проект является микросервисным;
- что реализована полноценная административная панель;
- что транспорт уже защищён HTTPS, если deployment запускается через HTTP;
- что тестами покрыт весь проект.

Корректная формулировка: проект является модульным монолитом, основной пользовательский сценарий реализован для клиента и мастера, а автоматические тесты сосредоточены на ключевой бизнес-логике бронирования.
